## 必須修正
1. 方案A是臨時容器熱修，不是持久化映像部署。restart保留同一容器可寫層；移除/重新建立容器會失去該層。compose up -d不保證重建映像，更新NAS主機檔也不會讓舊映像自動帶入修復。撤回「之後up -d/重建必然保留」說法。若採A必須明列容器重建前須完成受控映像固化，不能宣稱正式交付已持久化。
2. 優先提出基於已確認部署映像ID/digest的單檔衍生修復映像：只COPY已審helper、維持原設定，使用獨立標籤與受控compose override。先確認容器可寫層是否有其他必要程式熱修；有差異不能假設衍生自舊映像即可保留。此階段僅設計與預檢清單，不執行。若仍列完整重建方案，程式檔相同不足以保證相同映像，還須控制基底映像、依賴、Dockerfile、build context/.dockerignore及設定。
3. 線上仍舊版改為「本次未部署，線上實際版本待唯讀核對」。本機HEAD雜湊僅比較基準，不能當遠端實測。記錄image ID與container ID，而不僅容器名。
4. Python3.11尚未驗證：在不掛正式資料的可丟棄環境以相符執行環境跑已接受的兩個檔案，屬部署相容性檢查，不重開產品修復、不跑完整套件。若環境不可用如實列為未測。
5. 容器Up/首頁200不等於API就緒。補後端就緒與合法匯出檢查。備份使用每次唯一名稱、避免覆蓋原備份，先記錄檔案權限；回退恢復漏洞的警示保留。不要依賴「檔案大小會使pyc失效」作通用部署保證。
6. 不索取或寫入sudo/正式站密碼；如需特權由使用者在自己的終端輸入。正式登入不是一般性禁止代操作，但本批仍不登入/執行部署。

## v2 審閱補註（2026-10-07）
方向接受：以部署映像為基底的單檔衍生映像、回退標籤與override可解決v1持久化問題。產品PASS不變，部署文件仍需以下限域更正；不另開產品測試輪。

1. **build context 非兩檔**：§3把所有預檢輸出写入W，§4卻docker build W。另建W/context，只放Dockerfile/helper；logs、備份與設定輸出留在context外。建置前核對檔案清單。image Config.Env 不應原文印進交接或聊天；比較時輸出相同/不同與鍵名，必要原始設定僅受限保存在本機，不把秘密帶入context。
2. **相容性指令退出碼**：§8最後 echo exit=$? 令容器以echo成功退出，即使pip/pytest失敗。改成明確保存執行鏈狀態、輸出後exit該狀態；安裝失敗不可繼續或誤稱pytest完成。執行前也先確認requirements-dev.txt與HTTP測試依賴（如httpx）完整。無環境即可維持未測，不為改指令安裝/啟動環境。
3. **部署前尚待確定項目變成門檻**：選定實際compose執行器、原專案名、原啟動使用的env-file/所有override後，再產生精確切換與回退指令；不能把帶方括號的選用參數當可直接執行。核對effective設定的volumes/env/networks等與目前運作服務一致，預期只改backend image。目前僅查版本尚不足以證明重建會保留執行設定。以不洩漏秘密方式核對；未確認前不得切換。
4. **探針限度**：401只支持驗證路徑可達，不能單獨證明完整應用就緒或修復載入。把body/header與已知後端回應核對；404/5xx/逾時/非預期回應均列異常，不只502/530。容器內根路徑、image/helper雜湊、合法匯出保留。nginx靜態upstream為backend:8000；若容器重建後容器內正常但代理502，先診斷名稱/IP解析及上游連線，不直接斷定helper故障；任何代理reload需在核准的執行範圍。
5. **STATUS舊措辭**：可在目前STATUS尾端附日期更正「本批未部署，線上實際版本未核對」，保留已封存檔原文不動。封存是歷史快照，不要求活文件永遠複製過時說法。

此輪僅修改部署文件/現況補註，不執行遠端預檢、映像建置或部署。修正後不需再逐輪延伸設計；待使用者明確部署指示時才執行預檢並帶回未知事實。
