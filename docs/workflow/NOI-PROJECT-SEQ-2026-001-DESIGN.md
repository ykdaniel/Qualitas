## 現況（讀碼）

**編號怎麼產生**
- `generate_reference_no(db, vendor_name, 'NOI')`
- 命名規則表 `document_naming_rules` 的 noi 前綴預設是 `QTS-RKS-[ABBREV]-NOI-`，6 碼；設定頁可以改，但必須含 `[ABBREV]`。
- 序號表 `reference_sequences` 的 key 是 `(project, vendor, doc)`，其中 `project` 一律填常數 `QTS`（core/constants.PROJECT_CODE），所以**同一家承包商的 NOI 跨所有專案共用一條流水號**。
- 另有 self-heal：取 `max(last_seq, 資料表中同前綴的最大號)+1`。

**唯一性**：`noi.referenceNo` 全表唯一。ITR、Checklist、NCR、OBS、Follow-up 都是用這個號碼引用 NOI。

**專案**
- `projects.code` 是選填的自由文字，不要求唯一，目前只有 Audit 拿來顯示。
- **NOI 表單沒有專案欄位**：
  - 不受限的使用者建立的 NOI，`project_id` 一律是空的；
  - 只限定 1 個專案的使用者，會由 `enforce_create_scope` 自動帶入；
  - 限定 2 個以上專案的使用者，建立 NOI 會被 403 擋下（「project_id is required」）。這是既有的缺口。
- ITP 和 FAT 的新增表單已經有共用的專案欄位 `CreationProjectField`。

**正式站**：NOI 目前 0 筆（使用者已刪掉測試資料），所以實務上是乾淨的起點。

## 1. 編號格式

新增命名規則代號 `[PROJ]`，代表專案代碼。noi 前綴改成必須同時含 `[PROJ]` 和 `[ABBREV]`。

| 選項 | 新 NOI 前綴 | 範例 | 說明 |
|---|---|---|---|
| A（建議） | `QTS-[PROJ]-[ABBREV]-NOI-` | QTS-KHL2-FHS-NOI-000001 | 用專案代碼取代原本的常數 RKS，長度幾乎不變。前提是 RKS 本身沒有要保留的意義。 |
| B | `QTS-RKS-[PROJ]-[ABBREV]-NOI-` | QTS-RKS-KHL2-FHS-NOI-000001 | 保留 RKS，多一段，號碼較長，列印和清單欄位要確認寬度。 |
| C | 由使用者在設定頁自訂 | — | 程式只規定 noi 前綴必須含 `[PROJ]` 和 `[ABBREV]`。 |

**設定頁（文件命名規則）**
- 說明文字加上 `[PROJ]`。
- noi 的前綴若缺 `[PROJ]`，前後端都拒絕存檔，否則不同專案會撞號。
- 其他模組先不強制。

**專案代碼**
- 有 NOI 的專案必須設定代碼。
- 代碼格式：2–8 碼英數字，存成大寫。
- 代碼全系統唯一：需要 migration，在 `projects.code` 非空值上建唯一索引。
- 專案管理頁：
  - 新增、修改專案時檢查代碼；
  - 沒有代碼的專案旁邊顯示提示「設定代碼後才能建立 NOI」。
- 建立 NOI 時，所選專案若沒有代碼就拒絕，訊息會提示請管理者到專案頁補上。
- 代碼建議設定後就不再更改。即使更改，因為序號 key 用的是專案 id（見第 2 點），流水號會接續、不會撞號，只是前綴會改變。

## 2. 舊資料與序號

**舊 NOI 的號碼一律不改**，因為其他文件都是用號碼引用 NOI。

**序號表**
- NOI 的 key 改成 `(project=<專案 id>, vendor=<承包商縮寫>, doc='NOI')`。用專案 id 而不是代碼，是為了改代碼也不會重新從 1 開始。
- 其他模組照舊用 `QTS`。
- 不需要改資料表結構，`project` 欄位本來就是字串。
- 舊資料列 `(QTS, X, NOI)` 留著不刪，供「沒有專案」的舊情況和回溯查詢使用。

**從哪裡起算**
- 新前綴和舊前綴不同，每個「專案＋承包商」都從 000001 起算。
- self-heal 改用新前綴查最大號。新前綴含專案代碼，不會誤抓到別的專案的號碼。

**為什麼仍然以承包商分開計**：如果只按專案計（不分承包商），只能看到自家的承包商使用者，就能從號碼推出同專案裡其他承包商開了幾張 NOI，等於出現新的洩漏。所以維持「專案＋承包商」。

## 3. 沒有專案的 NOI

| 選項 | 做法 |
|---|---|
| A（建議） | **新建 NOI 一律必須選專案。**<br>• NOI 表單加上和 ITP 相同的 `CreationProjectField`，預設帶入所選 ITP 的專案（ITP 本來就有 project_id），沒有的話帶目前切換的專案。<br>• 若 ITP 有專案，NOI 的專案必須和它一致。<br>• 批次新增（/noi/bulk/）的每一列也都要有專案。<br>• 同時修好「限定 2 個以上專案的使用者無法建立 NOI」的缺口。 |
| B | 允許不選專案，不選時沿用舊的全域流水號（QTS-RKS-ABBREV-NOI-）。<br>• 兩套號碼並存；<br>• 不選專案的 NOI 仍有 R3 的洩漏。<br>不建議。 |

**舊 NOI（專案為空）**
- 號碼不動。
- 可以補填專案，但號碼保留，比照 2026-10-10「舊資料補填承包商時保留號碼」的決策。

**建立後改專案**：建議比照承包商規則。
- 已有文件引用時，不得更改。
- 沒有引用時可以改，改了就用新專案重新編號。
- 另一個選擇是建立後完全鎖定專案，比較簡單。

## 4. 預計編號端點和 #8 遮罩

改成按專案計之後，號碼只透露「這個專案、這家承包商」的張數。

**建議**
- `GET /noi/next-reference` 加上必填參數 `project_id`。
- 專案必須在呼叫者的範圍內，否則回 403。
- 承包商範圍的使用者照舊只能查自家承包商。
- 只限定專案的使用者看到的，是自己專案裡的張數；這些 NOI 他們本來就看得到，不算洩漏。
- 所以 **#8 遮罩可以拿掉**，所有人都看到完整的預計編號。`pattern` 欄位保留，在還沒選專案或專案沒有代碼時顯示格式。

**R3 列出的其他途徑也一併關閉**
- 建立後拿到號碼：只看到自己專案的張數。
- 改承包商重新編號：也是在同一個專案內。
- 看既有號碼：同上。

## 5. 其他模組（只提建議，這批只做 NOI）
- **同一條鏈（ITR、Checklist、NCR、OBS）**：建議下一步跟進。
  - 它們的號碼目前也是「承包商跨所有專案」計算，同樣有 R3 的洩漏；
  - 而且 ITR 和 Checklist 的專案可以從 NOI 推出來。
  - 建議做法和 NOI 相同：`[PROJ]`＋（專案 id, 承包商, 類型）。
- **ITP、PQP、FAT、Audit、Material、Meeting、OSD、Follow-up**：風險較低，或本身已經和專案綁定。等 NOI 和上面那條鏈穩定後，再逐一評估。
- **共用工具**：`generate_reference_no` 加上選填參數 `project_id`；沒傳時維持舊行為。這樣其他模組可以一個一個切換。
