# ITP-AUTOFILL-INTERACTION-2026-001 — NOI 廠商聯絡資訊填表互動方案（設計提案）

延續 ITP-AUTOFILL-INVENTORY 系列盤點（已 PASS 結案，完整原文見
`docs/workflow/ITP-AUTOFILL-INVENTORY-2026-002-archive.md` 與其補註更正）。
**本批是設計提案，暫不修改任何產品程式碼、不建立任何資料。**

**範圍明確僅限 NOI。ITP 本身沒有 `contactPerson`/`phone`/`email` 這類欄位可以
承接，不建議為了自動帶入去新增一個目前沒有實際用途的欄位——這是 ITP-AUTOFILL-
INVENTORY-2026-001 已確認的事實，本輪沿用，不重新查核。**

## 核心問題：現有「只填空欄」guard 解決不了的事

盤點已確認（見上述補註）：`prev.contacts || selected?.contactPerson || ''` 這個
guard 只能回答「這個欄位現在是不是空的」，答不了「這個值是系統帶的、還是使用者
自己打的」。換廠商時，已經被系統帶過一次的舊資訊會被誤判成「使用者已經填過」，
於是錯誤地被保留下來。要同時做到「換廠商不殘留舊資訊」和「不覆蓋使用者自己打的
字」，必須多記一件事：**每個欄位目前的值是系統帶的，還是使用者自己動過的**。

## 方案：每個欄位多記一個「來源」狀態

概念上，`contacts`／`phone`／`email` 三個欄位各自多一個內部狀態（不是新的 DB
欄位，只是前端表單暫存狀態，隨這筆正在編輯的 NOI 一起消失，不持久化）：

- **`system`**：目前顯示的值是系統從某個廠商帶入的，使用者還沒有自己動過。
- **`user`**：使用者自己打過字（不論是整段改掉、還是打了又刪只剩空字串）。

### 1. 選定廠商後如何帶入

- 新建 NOI、尚未選過廠商時：三個欄位狀態都是空＋`system`（還沒有值，但視為
  「可以被系統填」的狀態）。
- 使用者選定廠商 A：若某欄位目前狀態是 `system`（不論現在是空還是之前被某廠商
  帶過），就把該欄位的值換成 A 的對應資料（`contactPerson`/`phone`/`email`，
  若 A 本身這個欄位是空的，就清空該欄位），狀態維持 `system`。
- 若某欄位目前狀態已經是 `user`，**完全不動**——不論選哪家廠商都一樣。

### 2. 換廠商時如何避免錯配與覆蓋

這正是上一輪補註指出的風險，本方案的解法：

- **換成 B 廠商、使用者完全沒碰過聯絡資訊三欄位**（狀態仍是 `system`）：原本
  顯示的是 A 的資訊，換成 B 之後，三欄位**重新**套用上面第 1 點的規則，改成
  B 的資訊——不會殘留 A 的舊資料，解決了錯配風險。
- **使用者已經手動改過其中任一欄位**（例如把電話改成自己另外問到的號碼，狀態
  變成 `user`）：換廠商時這個欄位**不會**被 B 的資料覆蓋，其餘還是 `system`
  狀態的欄位仍會照常更新成 B 的資料——三個欄位的狀態是分別獨立記的，不是
  整組一起鎖住或一起放行。
- 欄位從 `system` 變成 `user` 的時機：使用者在 `contacts`/`phone`/`email`
  這三個輸入框本身打字（`onChange`）的當下，不分是改掉還是刪空，都視為
  `user`（跟現有「打了又刪也算使用者動過」的既有限制一致，不是本輪新引入的
  行為）。

### 3. 畫面提示文字與 A→B 範例

本輪沒有找到既有的「系統帶入值」視覺樣式可以直接沿用（上一輪盤點已確認），
以下是新提案，刻意保持最小：在 `contacts`/`phone`/`email` 三個欄位下方，狀態
為 `system` 且目前有值時，顯示一行小字提示（與既有欄位說明文字同樣大小/顏色的
灰色小字，不是新的視覺元件）：

> 由廠商資料帶入，可直接修改 (Auto-filled from the contractor — edit if needed)

欄位狀態一旦變成 `user`，這行提示就消失。

**具體操作範例**：
1. 使用者新建一筆 NOI，選擇 Contractor 下拉選單，選了「永昌營造」。
2. `contacts` 顯示「王小明」、`phone` 顯示「0912-345-678」、`email` 顯示
   `wang@yungchang.example.com`，三個欄位下方都出現「由廠商資料帶入，可直接
   修改」的灰色小字。
3. 使用者發現這次現場聯絡窗口不是王小明，把 `contacts` 手動改成「李大華」——
   `contacts` 下方的提示文字消失；`phone`／`email` 維持原樣、提示文字仍在。
4. 使用者發現廠商選錯了，把 Contractor 改選成「永昌營造」旗下的另一家合作廠商
   「永昌營造(北區)」。此時：`contacts` 因為已經是 `user` 狀態（剛才手動改成
   李大華），**維持「李大華」不變**；`phone`／`email` 因為還是 `system` 狀態，
   自動換成「永昌營造(北區)」的電話與 Email。
5. 使用者存檔。這筆 NOI 存的就是：廠商＝永昌營造(北區)、聯絡人＝李大華（使用者
   自己改的）、電話／Email＝永昌營造(北區)主檔當下的資料。

### 4. 既有歷史紀錄維持原值

這個「來源狀態」只存在於**正在編輯**的表單暫存狀態裡，不寫進資料庫，也不是
NOI 本身的欄位。打開一筆**既有**的 NOI 編輯時，`contacts`／`phone`／`email`
三個欄位直接顯示資料庫裡存的值（跟現在完全一樣），狀態視為 `user`（已經是
使用者/系統在當時確定下來的值，不是這次表單工作階段系統剛帶的）——這樣即使
之後去編輯這筆既有 NOI 又順手換了廠商，也不會因為這個新機制而被意外改掉既有
的聯絡資訊；Contractor 主檔事後更新（例如永昌營造換了新的聯絡人）同樣**不會**
回頭影響任何已經存在的 NOI 顯示內容——這點與現狀完全一致，本方案沒有改變。
