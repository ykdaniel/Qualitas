# KM 主文章成功、章節失敗後重試（2026-09-30）

## 根因與範圍
讀碼發現 KMModal 每次保存均依原始 id prop 判斷建立或更新；主文章成功但後續章節失敗時，沒有保存回傳的主文章 id/version_no。新建重試可能再次 POST 主文章；既有文章則沿用過期 version_no 而被拒。章節本身已有逐步記錄成功 id/version 的機制，本輪保留。

新增 writeKMMain 供正式表單呼叫，以同一 Modal 的 ref 保存確認成功的主文章 id/version；失敗不推進，新建成功後重試改 PUT 同一 id，使用最新版本號及當下表單內容。不同紀錄初始化時重設；未新增去重後端或放寬權限。

主文章成功但章節未完成時，顯示結果未確認的友善提示並保留輸入。不再直接顯示後端原始例外。主資料失敗顯示既有通用保存失敗提示。

## 證據層級
- 修正前根因為靜態讀碼，不宣稱修正前瀏覽器重現。
- 兩項正式 helper 單元測試：新建確認成功後重試只更新同一 id/最新內容；失敗不推進版本、連續成功使用最新版本號。模擬章節失敗，不宣稱完整表單測試。
- 真實獨立 8202/3202 堆疊：既有文章 version1，update-only 帳號改章節名稱觸發子章節建立真實403；主文章 PUT200/version2、視窗/輸入保留，部分成功提示正確。再改名稱重試：主文章 PUT200/version3、子章節仍403（不是主文章409），文章仍只有原id一筆。將章節名改回主文章名，消除新增子章節需求，再保存成功正常關閉，version4。
- 未模擬伺服器已提交但回應遺失；不保證該情境下新建重試冪等。
- 新建 POST→章節失敗→PUT 路徑本輪為 helper 測試，未另跑新建畫面案例。

## 同輪：KM 刪除失敗與處理中狀態
KM 原本 await deleteKM 後無 catch，失敗未顯示提示。現改為捕捉例外、單一友善 toast、保留視窗，finally 恢復操作；ref 擋住處理中重複送出。共用 ConfirmModal 新增選用 pending（預設 false），KM 刪除期間停用確認/取消/關閉及遮罩關閉，其他呼叫端預設行為不變。

獨立測試角色先取得刪除入口，再由隔離種子撤回該角色 delete 權限（不刷新前端），點擊確認得到真實 DELETE403：顯示 Delete failed、確認視窗仍在、按鈕可用；唯讀 DB 確認原文章仍是同id/version4。未執行成功刪除，未對慢回應實測pending時的按鈕狀態；pending屬讀碼核對。種子參數 `-- --allow-delete` / `-- --deny-delete` 僅用於該隔離角色。
