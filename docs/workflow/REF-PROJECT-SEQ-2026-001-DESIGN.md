## 1. 專案從哪裡來：登入時決定，前端帶入，後端強制

### 現況（讀碼）
- **前端**：「目前專案」只存在 localStorage 的 `qualitas_current_project`，是整個 Project 物件（`store/projectStore.ts:30-67`）。
  - 右上角的 `ProjectSelector` 對所有人都有「所有專案」選項。
  - **登出時不會清掉這個值**（`AuthContext.tsx:67-73`），下一個在同一台瀏覽器登入的人，會沿用上一個人的專案。
- **後端**：沒有「目前專案」這個概念，只看每次請求帶的 `project_id` 參數，再和範圍取交集（`core/scope.py`）。
  - JWT 只有 `sub` 和 `user_id`。
  - `compute_scope` 規則：
    - admin／administrator 角色：不受限；
    - **沒有 UserProject 也沒有 vendor：不受限**，這就是 D6 要修的漏洞；
    - 其他人：依綁定的專案和承包商限制。

### 設計
1. **登入流程**
   - 非管理者：
     - 只綁 1 個專案：直接進入。
     - 綁多個專案：登入成功後顯示「選擇專案」畫面，只列出自己綁定的專案。
     - 綁 0 個專案：進入「非專案人員」畫面（D6）。
   - 管理者：登入後依目前的選單使用，可以選「所有專案」或任一專案。
2. **「選定專案」由伺服器記錄，不只放在前端**（建議）
   - 非管理者選定專案後，後端發出的 JWT 帶上 `project_id` claim；`compute_scope` 對非管理者只用這個專案。
   - 這樣即使有人改 localStorage 或請求參數，也看不到自己綁定的其他專案，符合 D5「之後不能換」。
   - 換專案的方式是登出再重新登入。
   - 管理者的 token 不帶專案，照舊用請求參數。
3. **compute_scope 改寫**
   - 管理者：不受限。
   - 非管理者：範圍＝ token 裡的那個專案，而且必須仍然是他綁定的專案；有綁承包商的話再加承包商限制。
   - 沒有專案時：**空範圍**，所有清單都是空的、詳細頁回 404、新建回 403。
   - 專案綁定被移除時，下一次請求就失效，前端會導回「非專案人員」或「選擇專案」畫面。
4. **右上角選單**
   - 管理者：維持現在的選單，包括「所有專案」。
   - 非管理者：只顯示「目前專案：XXX」，旁邊註明「切換專案請重新登入」，不能點選。
5. **登出時清掉 `qualitas_current_project`**。登入後也要核對：存著的專案必須在該使用者的範圍內，否則清掉。這是既有的錯誤，一併修。
6. **IAM**
   - 建立和編輯非管理者帳號時，專案必填，至少一個；承包商帳號也一樣（D8）。
   - 後端也要擋，不能只靠前端。

## 2. 新建單據：專案必填

- **前端**：新建時的專案＝目前專案。
  - 非管理者：token 裡的專案。
  - 管理者：右上角選定的專案。
  - 表單上唯讀顯示專案名稱。
  - 管理者選「所有專案」時，「新增」按鈕停用，滑鼠移上去提示「請先在右上角選擇專案」（D7）。
  - ITP 和 FAT 現有的專案下拉，改成唯讀顯示。
- **後端**：所有新建端點都要求 `project_id`。
  - 缺少：回 400。
  - 不在範圍內：回 403。
  - 取號一律在範圍檢查**之後**。目前 Checklist 是先取號，會在被 403 擋下時浪費號碼，一併修正。
- **從來源單據產生**：後端從來源帶入專案，而且必須和目前專案一致，否則拒絕。

| 產生方式 | 專案來源 |
|---|---|
| NOI → ITR | NOI |
| ITR → NCR | ITR |
| 重新檢驗 ITR | 原 ITR |
| ITR → Checklist 實例 | ITR |
| 手動 Checklist | ITR，否則目前專案 |
| 會議記錄 → Follow-up | 會議記錄 |
| 其他來源 → Follow-up | 來源單據 |
| 延續會議 | 原會議 |
| Q-WorkFlow | NOI |

- **引用共用 ITP 範本時，不從 ITP 帶專案**：NOI 引用共用範本，專案仍然是目前專案（修正 v1 的「NOI 由 ITP 帶入」）。
- **關聯一致性檢查**：存檔時，後端檢查連結的單據必須屬於同一個專案；ITP 例外，可以是共用範本。
  - ITR→NOI、NCR→ITR／NOI、Checklist→ITR、Follow-up→來源、NOI→ITP（同專案或共用）。
  - 目前只有 Material 有這種檢查（`material_submittal_service.py:195`）。

## 4. 編號規則

**格式**：`QTS-RKS-[PROJECT]-<類型>-######`（D2）
- 例：`QTS-RKS-HL-NOI-000001`；新專案 `QTS-RKS-TECO-NOI-000001`。

**命名規則與設定頁**
- 佔位符改成 `[PROJECT]`，取代原本的 `[ABBREV]`。
- 預設前綴改成 `QTS-RKS-[PROJECT]-ITP-`、`…-NOI-`、`…-ITR-`、`…-NCR-`、`…-OBS-`、`…-PQP-`、`…-FUI-`、`…-FAT-`、`…-AUD-`、`…-CHK-`、`…-OSD-`、`…-MOM-`、`…-MSA-`。
- 設定頁說明 `[PROJECT]`，並以目前專案預覽號碼。已切換到依專案編號的類型，前綴缺 `[PROJECT]` 時，前後端都拒絕存檔。
- 正式站現有的命名規則資料列，會由 migration 改成新前綴。改之前先匯出舊值，作為回滾用。

**沒有規則時的退路**
- 目前：`core/constants.PROJECT_CODE="QTS"`，退路格式是 `QTS-{ABBREV}-{DOC}-`，**沒有 RKS**。
- 改成：退路一律是 `QTS-RKS-{PROJECT}-{DOC}-`。公司代碼放進常數 `COMPANY_CODE="RKS"`，`PROJECT_CODE` 改名為 `SYSTEM_CODE="QTS"`。這樣沒有規則時也不會出現少了 RKS 的號碼。
- 呼叫端只會在命名規則表被清空時走到退路；設定頁讀取時本來就會自動補齊缺少的預設規則。

**序號**
- key：`ReferenceSequence(project=<專案 id>, vendor='*', doc=<類型>)`。用專案 id 而不是代碼，所以改代碼也會接續、不會撞號。
- 共用 ITP 範本：`(project='STD', vendor='*', doc='ITP')`。
- 舊的 `(QTS, 縮寫, doc)` 資料列留著不動，不再寫入。

**不分承包商的取捨**（D2）
- 同專案的所有承包商共用一條流水號。
- 承包商帳號可以從號碼推出同專案的總張數。協調中心已向使用者說明，使用者接受。
- 這同時解掉一個既有問題：編號的承包商縮寫和實際承包商可能對不上。

**撞號與起算點**
- 新號一律是「該專案、該類型、同前綴的現有最大號 +1」：沿用並強化 self-heal（`_max_existing_seq`，以新前綴比對），並把 Follow-up 補進對照表。
- Hailong（HL）的實例：舊號 `QTS-RKS-HL-*` 裡的 HL 原本是承包商 Hailong 的縮寫，前綴剛好和新格式的 Hailong 專案一樣。
  - ITR 最大 000002、NCR 000001、OBS 000001、CHK 000002、AUD 000005：新號自動接續，例如 ITR 從 000003 開始。
  - **ITP**：61 筆 `QTS-RKS-HL-ITP-*`（最大 000075）會改成 STD（第 5 節），改完後這個前綴就沒有任何資料。為了避免舊號被重複使用，migration 會把 `(Hailong, ITP)` 的序號設為 75，所以 Hailong 第一張專案 ITP 是 `QTS-RKS-HL-ITP-000076`。
  - 測試要涵蓋：前綴相同時接續、self-heal 不會被其他前綴誤導、新專案從 1 開始、兩個專案不會撞號、改代碼後接續。
- **新舊格式在同一個位置有不同意義**：
  - 舊格式（4 段＋流水號）`QTS-RKS-<承包商縮寫>-<類型>-` 的第 3 段是承包商；
  - 新格式 `QTS-RKS-<專案代碼>-<類型>-` 的第 3 段是專案。
  - Hailong 剛好兩者都是 HL，所以舊號在新規則下會被當成 Hailong 專案的號碼。字串唯一索引確保不會重複。
- **專案代碼**
  - 必填、唯一、2–8 碼英數字、存成大寫。
  - `STD` 是保留字，任何專案都不能用。
  - 有單據之後不建議再改，專案管理頁會提示。
  - migration 會在非空值上建唯一索引，必填由應用程式檢查。
- **建立後改專案**
  - 號碼含專案代碼，所以有號碼之後**鎖定專案**。選錯的話，作廢後重開。
  - NOI 改承包商不再重新編號，因為號碼裡已經沒有承包商。原本「已有文件引用就不能改承包商」的規則保留。

**特殊編號**

| 編號 | 處理 |
|---|---|

## 5. 共用 ITP 範本與 STD 改號（一次性轉換）

**怎麼區分兩種 ITP**（建議）
- `project_id` 為空＝共用範本；有值＝專案 ITP。
- 不另外加 `is_template` 欄位，因為兩者的差別剛好就是「有沒有專案」，而且正式站的 144 筆本來就都是空的。

**權限**
- 共用範本只有系統管理者能新增和修改，其他人只能看和引用。
- 專案 ITP 依現有權限，在自己的專案內新建。

**怎麼新建共用範本**（待確認，見 Q3）
- 建議：管理者在右上角選「所有專案」時，ITP 頁是唯一可以新增的地方，新增的就是共用範本。這是 D7「所有專案時不能新建」的唯一例外。

**引用**：NOI 選 ITP 時，列出目前專案的專案 ITP，再加上全部共用範本。

**STD 改號**（D11）
- **範圍：63 筆**，其餘 81 筆外部文件號不動。
  - 61 筆 `QTS-RKS-HL-ITP-*`；
  - `TEST-1`；
  - referenceNo 為 NULL 的 1 筆。
- **排序**（D11「照號碼排」）：
  1. 61 筆依原流水號的**數值**由小到大，對應 `QTS-RKS-STD-ITP-000001`～`000061`。原號有跳號，新號是連號。
  2. 接著是 `TEST-1` → `000062`。
  3. 最後是 NULL 那筆 → `000063`。
  - 前綴只有一種（`QTS-RKS-HL-ITP-`），所以字串排序和數值排序結果相同；仍然以數值排序實作。
- **引用同步**（盤點結果）

| 欄位 | 處理 |
|---|---|
| `noi.itpNo` | 指向 itp.referenceNo 的外鍵，但 SQLite 沒有啟用外鍵約束，也沒有 ON UPDATE。正式站有 1 筆，**用原生 SQL 同步改號** |
| `followup.sourceReferenceNo`（sourceModule='ITP'） | 正式站 0 筆；仍然寫進轉換邏輯 |
| `itr.detail_data` 舊版的 `"itpNo"` 鍵 | 正式站 0 筆含 `-ITP-`；仍然掃描，有的話一併改 |
| checklist.itpId、attachments.entity_id、RelatedDocuments、`?reopenItp=` | 用的是 ITP 的 uuid，不受影響 |
| `audit_logs`（entity_type ITP 共 125 筆，以及 NOI 的 itpNo 歷史） | **不改**，保留歷史原貌，用對照表追查 |
| `itr_approval_events` 快照 | **不改**：只能新增、ORM 禁止修改，而且有 sha256 驗證 |
| 前端 `/itp?openId=<號碼>` 和 Follow-up 深連結 | 舊書籤會失效。使用者表示系統還沒送出任何文件，影響可以接受 |

- **轉換方式**：在 `db_migrations` 新增一個步驟，用 `migration_flags` 確保只跑一次，所有動作在**同一個交易**完成：
  1. 寫入對照表；
  2. 因為有唯一索引，分兩段改號：先改成暫時值，再改成正式新號；
  3. 同步改上表列出的引用；
  4. 每筆寫一則 `audit_logs`（system-migration，附原因）；
  5. 設定序號：STD = 63、(Hailong, ITP) = 75；
  6. 寫入 flag。
  - 任何一步失敗就整筆 rollback。
- **對照表**（建議）：新資料表 `itp_renumber_map(old_referenceNo, new_referenceNo, itp_id, migrated_at)`。保留在資料庫裡，可以查詢、可以回溯；部署時另外匯出一份 CSV 存進部署紀錄。
- **演練**：先在隔離環境，用正式資料庫的唯讀複本完整跑一次，比對：
  - 144 筆的內容雜湊不變（只有 referenceNo 改變）；
  - 63 筆新號正確；
  - NOI 引用正確；
  - 81 筆外部號不變。
  - 正式上線前先備份資料庫。
- **之後新建的共用範本**：從 `QTS-RKS-STD-ITP-000064` 開始。外部文件號類型的範本怎麼處理，見 Q2。

## 6. 舊單據歸到 Hailong（D13）
- 一次性 migration，同樣用 `migration_flags`，在同一個交易內完成。
- **歸到 Hailong**：把 noi、itr、ncr、checklist、obs、osd、pqp、followup、meeting_minutes、audits、qworkflow 的 `project_id IS NULL` 都設為 Hailong。正式站約 16 筆。
