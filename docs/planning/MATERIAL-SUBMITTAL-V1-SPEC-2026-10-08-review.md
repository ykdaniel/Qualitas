## REQUIRED_FIXES

### R1 附件權限與分段保存需一致
§3.4 將 material_rev 的 update 權限固定為 manage，但 §4.1 宣稱 record_result 可上傳回覆文件。現有 require_attachment_permission 只依 entity_type 選一組 view/update，沒有 category 分權，所以 record_result-only 帳號實際上傳將被拒絕，manage-only 卻可能修改回覆文件。
請明定送審分類使用 manage、replyDocument 使用 record_result，並提出僅針對新 entity 的明確整合方式，涵蓋 upload/delete、scope 和狀態鎖，不擴大其他模組權限。Draft 禁止 replyDocument 也要有具體後端規則，不能只列 Submitted 的鎖。
補驗收：view-only、manage-only、record_result-only、兩者都有四組權限 × Draft/Submitted/有結果；附件上傳成功但 result 失敗時，UI 應如實提示「文件已上傳，結果尚未登錄」，重試不重複上傳。上傳/刪除與送出/登錄結果的競態須在寫入時把關，不能檢查完 Submitted 後等長時間上傳完成才不經重驗寫入已鎖版。

### R2 子資源、範圍與一致性契約
每個 /submittals/{id}/revisions/{revId} 動作須同時驗證 revision.submittal_id == id，且父子 project_id/vendor_id 一致；scope 只對 project/vendor 過濾，不會替你驗證父子歸屬。補「同專案另一份送審的 revId」與跨專案/跨廠商的替換測試，拒絕且零寫入。
對傳入 material_id：先檢查可見性，不可見回 404；可見但不同專案才回契約規定的 400，避免既有「一律 404」與跨專案 400 矛盾。明定 project/vendor 在送審建立後不可透過一般更新搬移，快照/actor/currentApproved/latest 等受控欄不可由 client 指派。
「同時最多一個未結版次」及結果只能登錄一次需有併發保護；請說明交易內重新檢查、unique/條件更新如何配合，補雙擊/併發建立新版、重複登錄、稽核失敗回滾驗收。currentApprovedRevision 必須屬於同一送審且有有效核准結果。AC-M2-7 的三種結果應分成獨立情境，不可對同一終態版次依序改結果。

### R3 新 schema 與首版可操作性
既有 camelCase 欄位不強改，但 AGENTS 對新 Model 欄位指定 snake_case；本批新表/新欄請按規則設計，API 命名另訂明確映射。`currentApprovedRevision_id` 不屬於既有相容性需求。
§3.6 不能只因舊模組使用 create_all 就把新 schema 全交給啟動時自動建表。請沿專案已有具名 migration 路徑，明列新表/新欄/索引/約束及 migration_owned 配合方式；不要求遷移舊架構或另換 migration 框架。補空庫、舊庫升級、重複執行與失敗回報，以及保留新業務資料的回退策略。
日期以實際日期型別驗證；專案天數 null 或非負整數，負數/非整數拒絕，自動日期由後端計算。專案天數未設定、手動日期缺漏的處理保留既定提案。
第一版「刪除送審＋回收編號」不是已確認需求，且需處理附件/循環 FK；建議先移出首版，避免以硬刪除和回收編號擴大範圍。送審列表 project_id 必填，與材料列表一致；分頁時明確定義看板數量/總數，避免只拿第一頁宣稱全量。

### R4 誤登更正的方案需可審查，不能以直接改庫為唯一替代
刪除「若不提供只能直接改資料庫」的二分法。這是需設計的更正流程，不能藉此推定使用者已接受撤銷權限與原因必填。
請提出最小方案並標待使用者確認：更正只修正本系統的登錄，不等於撤銷業主/顧問真正的核准；保留原結果、附件、操作者與更正歷程，不刪證據。需說明已有後續版次時是否拒絕撤銷、如何恢復有效的現行核准指標、重複/併發更正如何拒絕。不能無條件把指標恢復成當時舊值，可能蓋過後續已核准版。補上歷程 API/畫面怎麼查原結果，而不只寫 AuditLog 即視為使用者可查。

### 同批文件收尾及實作驗收注意（不用再開純文案審查輪）
1. §3.6「8 個索引」實列至少 9 個（括號內 ix_msre_revision_id 也是一個）；表格另寫 material_id index 卻未列入清單。實作前列出唯一一致的具名索引清單，數量由清單產生，不手估。驗證 unique 索引欄位與唯一性、one_open 的 WHERE 條件及必要 NOT NULL/PK 等約束，不能只驗名稱存在。補同名錯誤索引/缺必要約束的既有 schema 會停止且不破壞資料的 migration 測試。
2. §4.6 列表已明確選定專案，統一不可見 projectId 回 404，不留「實作再決定空清單或 404」；無條件可見者仍只能依請求專案篩選。材料 vendor scope 的限制不能只靠「首版不指派角色」：M1 必須明訂並落實對帶 vendor scope 帳號的處理；首版採保守拒絕本新模組，測試即使誤配材料權限也不會列出同專案所有材料。不改其他模組 scope。
3. 分段保存文案區分確定拒絕與結果未知：timeout/連線中斷可能已寫入成功，先重讀該版有效登錄與附件，無法確認時顯示「無法確認登錄結果」，不能一律顯示「尚未登錄」或盲目重送。這是 M2/M3 驗收條件，不阻擋 M1。
4. §3.5「不影響其他版次的核准」精確寫成「不改寫其他版次的歷史結果，但可能重新選定較早版為現行核准版」。保留附件無法在更正時替換的首版限制。
5. r2 仍引用 r1 多處，實作任務需附明確的有效 AC 清單；不可沿用已被取代的 CRUD/刪除要求。資料模型可預留追加結果紀錄，但在使用者決策前不提供更正端點或按鈕。
